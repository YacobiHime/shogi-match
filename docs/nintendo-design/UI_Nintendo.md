# UI_Nintendo ― 任天堂のUI論に基づくゲームUI作成方法

任天堂および関連スタジオ（HAL研究所など）が講演・インタビュー・採用情報で公開しているUI/UXの考え方と、それを紹介・考察した記事を整理したリファレンスです。

---

## 0. この文書について

### 0-1. 範囲

- 対象は「ゲームのUI」です。具体的には、本体メニュー、ゲーム内HUD、メニュー画面、ダイアログ、チュートリアル、ロード画面、効果音、UIアニメーションを含みます。
- 任天堂の公開情報を中心に、その周辺の資料も含めています。
  - HAL研究所（『星のカービィ』）の講演
  - ゲームニクス理論。HAL研究所出身のサイトウ・アキヒロ氏が、任天堂の品質審査「マリオクラブ」での経験をもとに体系化したもの
  - 講演参加者などによる個人ブログ・ノート
- 内容は各資料の要約・言い換えです。原文の詳細や図版は、末尾の出典リンクで確認してください。

### 0-2. 表記

- `[S1]` などは、末尾「12. 出典一覧」の番号です。
- 「0.2秒」「3つ程度」などの数値は、各製品での**事例**です。普遍的な基準値ではありません。
- 「→ 補足」と書いた部分は、出典の内容から導いた一般化や応用です。出典に直接書かれている内容ではありません。

### 0-3. 全体像

任天堂のUI論は、次の3つの軸と、それを支える開発プロセスにまとめられます。

| 軸 | 目的 | 代表的な考え方 |
|---|---|---|
| **明快** | 見てすぐわかる・迷わない | 簡単「そう」に見せる、迷わないルール、文字に頼りすぎない |
| **軽快** | 待たせない・手間をかけさせない | 理解・操作・処理の3段階で時間を削る、信頼と端的 |
| **快・娯楽** | 触って楽しい・魅力的 | 不快を減らしたうえで快を足す、あそび心、世界観 |
| （土台）**おもてなし** | プレイヤーの一歩先回り | 説明しないで教える、必要な瞬間に助ける |
| （土台）**プロセス** | 上記を実現する作り方 | 全員で触る、早く共有する、実際の人で確かめる |

## 1. 基本思想

### 1-1. UIは「ゲームと人をつなぐ接点」であり、情報を整理する仕事

- 任天堂は、UI/UXデザイナーの役割を「ゲームとお客様の接点のデザイン」と説明しています。その範囲は、タイトル画面、メニュー、体力ゲージ、マップ、アイコン、フォント、メッセージ、リザルト画面など、ゲーム内の情報全般です [S7][S8]。
- HAL研究所のカービィチームも、UIの役割を「プレイヤーとゲームをつなぐこと」と位置づけています。そのうえで、使いやすいUIとは情報をうまく扱えていることであり、UIデザインとは情報を扱い・整理する仕事だ、と整理しています [S6]。
- 任天堂のUI/UXデザイナーには、グラフィックデザインの素養に加えて、情報を編集する力と、お客様の行動や心理を観察する力が求められるとされています [S7]。

### 1-2. 「ツール」ではなく「娯楽」を作る

- わかりやすいことは前提です。そのうえで「より魅力的であること」も同じくらい重視されています [S7]。
- 日常のポジティブな感覚（ワクワク、うれしい）をヒントに、実用的で、かつ魅力的なデザインを目指すのが任天堂のUI/UXデザインの醍醐味だとされています [S8]。

### 1-3. 文字に頼りすぎない「わかりやすさ」

- 子どもから大人まで、普段ゲームをしない人も含めて使うことを前提にしています。そのため、文字情報だけに頼らないわかりやすさを追求しています [S7]。
- 説明なしで子どもやゲームに慣れていない人に使ってもらえたことが、デザイナーにとっての成功体験として語られています [S7]。

### 1-4. コンセプトを決め、「何を捨てるか」を決める

- Switchの本体機能では、他機種の多機能化の流れをいったん疑いました。そして「ゲーム機なのだから、ゲームで遊ぶことに特化する」という原点回帰を選んでいます。作るものを厳選して魅力を凝縮し、ストレスを感じさせないことを目標にしました [S1]。
- 当たり前に見えるコンセプトでも、市場の流れや過去の積み重ねに逆らって貫くのは簡単ではありません。切り捨てる決断が必要になります [S4]。
- Wiiの本体機能（Wiiチャンネル）の開発でも、仕様を決めるうえで本当に大事なのは「何を足すか」ではありませんでした。「何を捨てるか」「何をやらないと決めるか」が重要だったと振り返られています [S5]。

### 1-5. 「あたりまえ」も磨けば特徴になる

- 「明快で軽快」というコンセプトは特別なものではなく、どのプロジェクトでも目指すものです。それでも、徹底的に磨き上げれば製品の特徴になる、というのがSwitch本体機能チームの結論です [S1]。
- Switchのホーム画面は驚くような仕掛けがあるわけではなく、「普通に使いやすい」ものです。その普通さを実現するために、多くの工夫や発想の転換が必要だった、という見方が紹介されています [S4]。

### 1-6. 「不快を減らす」と「快を増やす」の両輪

- 明快・軽快は、ユーザーの**不快を減らす**取り組みです。これとは別に、娯楽商品の魅力として**快を増やす**ことも必要です [S1]。
- 快が多くても不快が多ければストレスになります。不快が少なくても快がなければ、娯楽としての魅力がありません [S1]。
- どちらを優先するか迷ったときの判断基準として、「さわりたい」と感じられるかどうかが挙げられています。コントローラを持って触りたくなる状態なら、快と不快のバランスが取れている、という考え方です [S1]。

→ 補足：まず不快を除き、そのうえで快を足すと、演出がわかりにくさを上塗りする事態を避けやすくなります。

## 2. 明快 ― 見てすぐわかる

### 2-1. 「簡単」と「簡単そう」は違う

- 1ボタンで済む操作でも、それが一目で伝わらなければ「簡単そう」には見えません。簡単かどうかを決めるのはユーザーです [S1][S3]。
- Switchのホーム画面では、多機能でありながら「簡単そう」に見せるために、次の4つの工夫をしています [S1][S2]。

| 工夫 | 内容 |
|---|---|
| ① 混ぜない | ゲームとサービス／システムを分けて配置する |
| ② サイズと密度 | ゲームのアイコンは大きく、デザインの密度を濃くする。その他は小さく、淡くする |
| ③ 上下の意識 | 優先度の高いものを上に置く |
| ④ 少なく見せる | レイヤーに分けたり区切りを付けたりして、数が多くても少なく見えるようにする |

- これらをまとめると「整頓とメリハリ」になります [S1]。
- 以前の機種（3DS、Wii U）では、ゲームもサービスもシステムも同じ大きさのアイコンで同列に並んでいました。Switchではこれを改め、「ゲームが主役」に見えるようにしています [S2]。
- ホーム画面は歴代機種と同様にニュートラルで安心感のある見た目を基本にしつつ、メリハリでまずゲームに目が行くようにしています [S1]。

### 2-2. 迷わないルールを先に作る

- Switch本体機能では、約400画面の実装が必要でした。画面ごとに役割は違っても、見た目と使い勝手は同じほうが使いやすいため、共通のルールを決める必要がありました [S1]。
- 基本姿勢は、**開発者が迷うことはユーザーも迷う**というものです。チームは開発中の「迷い」を見逃さないように気を付けていました [S1][S4]。

**カーソル移動の例**

- アイコンの下に複数のアイコンが並んでいるとき、下を押してどこに移るのが自然かは、人によって答えが違います。中央が自然だと思う人もいれば、左端だと思う人もいます [S4]。
- そこで出した答えは、アルゴリズムを工夫することではなく、**迷うような並べ方自体をやめる**ことでした。結果として、配置は基本的に横一列か縦一列になっています [S4]。
- 具体的なルールは次のとおりです [S1]。
  - デザイン側：一列に並べる／グリッドに並べる／種類を分ける
  - プログラム側：幅による探索、距離による探索、左上優先
- プログラムの課題（カーソルのアルゴリズム）の答えをデザイン（配置）に求めた点は、職種をまたいだ発想の転換として紹介されています [S4]。

### 2-3. メッセージは大きく分類し、見た目と音を揃える

- 当初、効果音は「案内」「注意」「確認」の3種類で考えていました。しかし、どれに当たるか判断に迷う場面が出てきました [S1]。
- そこでデザイン側が、メッセージの出現タイプを**正常系・エラー系・警告系**の3つに限定しました。効果音もそれに合わせて3タイプにし、見た目と音を揃えるルールにしています [S1]。
- ダイアログ以外でも、本体機能全体で見た目と効果音を一致させています。伝えたいことは**視覚と聴覚の両方で伝える**方針です [S1]。最終的な効果音は約300種類にのぼります [S1]。
- デザイン側が効果音に合わせて見た目を調整したケースもあります。カーソルの挙動や効果音のように別々の担当者が作るものは、担当ごとにルールを作ると不整合が起きやすくなります。そのため、ルールはチーム全員で磨くほうが効果的だと結論づけています [S1]。

### 2-4. 階層を深くしない

- Wiiチャンネルの開発では、ダウンロードしたゲームを機種別のフォルダに分けて階層化する案が当初ありました [S5]。
- しかし、少しでも速く起動して遊べるようにしたいのに、わざわざ深い場所に置く必要はない、と判断しました。買ったゲームは最初の画面に並んでいたほうがうれしい、という結論です [S5]。
- ゲームに興味がない人にとっても、天気やニュースの隣にゲームが並んでいるほうが気軽に手に取りやすい、という観点もありました [S5]。

### 2-5. 情報の優先度は場面ごとに変わる

- 『スプラトゥーン』のバトル画面では、キャラクターと背景（塗られた地面）が最も目立つ必要があります。そのためUIは地面を隠さないようにし、他の画面に比べてすっきりさせています [S10]。
- 『ゼルダの伝説 ブレス オブ ザ ワイルド』では、常時表示するUIを左上と右下に絞り、サイズも小さくしました [S9]。
- 同作では、武器の耐久値、操作ガイド、ルピーなどを「本当に常に必要か」と見直し、必要なときだけ表示するようにしています [S9]。
- ゲーム後半にハートが増えるなどして画面が窮屈になる問題には、常時UIをさらに減らせる「プロモード」をオプションとして用意して対応しました [S9]。

### 2-6. 「なければない方がよい」けれど「なくせない」

- 『ブレス オブ ザ ワイルド』のUIコンセプトは「なければない方がよいUI」でした。UIを使わずに快適に操作させる、という挑戦的な目標です [S9][S8]。
- ただし、UIの本質は情報を伝えることなので、完全になくすことはできません。そのため、**存在感は抑えつつ、伝えるべきことは印象的に伝える**という、一見矛盾する課題に取り組んだと説明されています [S8][S9]。
- 具体的には次のような工夫をしています [S9]。
  - アイコンやボタン表示から縁取りを外し、単色のシルエットにする
  - フォントも装飾をなくす
  - 気づいてほしい情報（ダメージでハートが減るなど）だけをアニメーションで強調する
- 続編『ティアーズ オブ ザ キングダム』では、さらにUIを薄くする方向も検討されました。最終的には、無味無臭にするのではなく、プレイヤーの感情に寄り添って世界への没頭を深める方向を選んでいます [S8]。

### 2-7. 構図で理解させる

- 『ブレス オブ ザ ワイルド』の装備画面では、左に装備品の一覧、右にリンク（主人公）のモデルを置いています。見ただけで「この装備を身に着けるとこうなる」と理解できる構図です [S9]。

### 2-8. 見やすさの確認方法（明度・彩度）

- 『スプラトゥーン』では、画面を白黒にして見やすさを確認していました。テキストやアイコンが白く浮き、背景がグレーに沈んでいれば見やすい画面です。目を細めて画面を見る方法もよく使われます [S10]。
- 目立たせたいアイコンは彩度を高く、それ以外は彩度を低くしています。テーマカラーのオレンジも、実際の下地には茶色系が使われていました [S10][S13]。

### 2-9. 「伝え方」の基本：情報過多も情報不足もUIとして成立しない

- 任天堂の新人UI研修では、大量の選択肢から5秒で答えを選ばせるクイズを出すそうです。答えが分かっていても選択肢が多すぎて見つけられず（情報過多）、正解として示されるのが番号だけでは意味がわからない（情報不足）。この体験を通じて、問題・回答・正解をうまく届けることがUIの基本だと伝えています [S10]。

## 3. 軽快 ― 待たせない・手間をかけさせない

### 3-1. 原点は「電源を入れればすぐ遊べた」体験

- 本体機能の開発では、社内で「ファミコンのようにならないのか」とよく言われたそうです。電源を入れるとすぐ遊べたファミコンの軽快さを目標に、UIにかかる時間で削れるものはすべて削る方針をとりました [S1]。

### 3-2. 停止距離モデル：理解 → 操作 → 処理

- 車が止まるまでの距離は、危険に気づくまで → ブレーキを踏むまで（空走距離）→ 止まるまで（制動距離）の合計です。これをUIに当てはめ、時間を**ユーザーの理解 → ユーザーの操作 → システムの処理**の3段階に分けて考えました [S1][S4]。
- 最も重視したのは、**どれか1つだけを削っても軽快にはならない**という考え方です [S1]。
- 内部処理の高速化は手段の1つにすぎません。ユーザー体験全体を見て、どこに問題があるのかを考える必要があります [S4]。

### 3-3. 処理：0秒を目指すが、速すぎると伝わらない

- システムの処理時間はユーザーにとって単なる待ち時間なので、0秒を目指して削りました [S1]。
- しかし、ただ速いだけでは何が起きたのか伝わりません。処理と表現のバランスを取った結果、ボタンを押してから処理が終わるまでが**約0.2秒**になりました [S1]。

### 3-4. 操作：信頼と端的

- 一般的なUIでは、誤操作を防ぐために「データを消去しますか？」に対して最初は「いいえ」にカーソルを合わせます（フェイルセーフ） [S1][S3]。
- Switchでは、ユーザーが「終了したい」と操作したら、本体側もそのまま「終了します」と応じる設計にしています。「本当に終了しますか」と聞き返すのは、ユーザーを信頼していない疑問形だ、という考え方です [S1]。
- ただし、この方法では誤操作の可能性をゼロにはできません。そこで、**わかりやすい表示によって誤操作を防ぐ**という手段をとっています（次項）[S1]。
- 個人の考察では、フェイルセーフを知識として知っているとこの発想にはなかなか至らない、と指摘されています。また、この設計は「ユーザーがUIにかける時間」という捉え方から生まれたのではないか、とも考察されています [S3]。
- **注意（誤読しやすい点）**：この事例でも、ソフトの消去などでは確認画面そのものは表示されています。変えたのは、**確認を出すかどうかではなく、初期カーソルの位置（実行側）と、文言・ボタンの書き方**です [S1]。「信頼と端的」は「確認ダイアログをなくす」という意味ではありません。

### 3-5. 理解：斜め読みで伝わる書き方

- 本体機能には多くの文章が必要ですが、人は斜め読みするものとして書かれています [S1]。
- **文章の左上（冒頭）に主題を置き、右下の決定ボタンに動詞を置く**ことで、最初と最後を読むだけで内容がほぼ誤解なく伝わります。このとき「はい／いいえ」ではなく、「キャンセル」「消去する」のように**ボタンを動詞にする**のがポイントです [S1][S3]。
- ナビゲーション部分にアイコンを置いていないのは、アイコンがあるとまずそこに目が行ってしまうからです [S1]。
- 丁寧ではあっても全文を読まないと意味がわからない文章は、軽快さを損なうとされています [S1]。

### 3-6. 待ち時間を価値ある時間に変える

- 『ブレス オブ ザ ワイルド』では、ワープ時のロード画面に冒険のヒントを表示し、待ち時間を実用的な時間にしていました [S8]。
- 『ティアーズ オブ ザ キングダム』では、旅行の計画で地図を広げるときのワクワク感をヒントに、ワープ先の地図をロード画面に表示しました。待ち時間が「次の冒険への準備時間」に変わったとされています [S8]。
- カービィシリーズでも、ロード画面の工夫が事例として紹介されています [S6]。

## 4. おもてなし ― 説明しないで教える

### 4-1. ゲームニクス理論

- サイトウ・アキヒロ氏は、HAL研究所で岩田聡氏らと仕事をする中で、マリオクラブなどの経験から、ゲームの面白さは操作性の良し悪しに大きく左右されると学んだと述べています [S14]。
- ゲームは**ストレスと快感のバランス**が基本です。ゲーム本来の内容以外でストレスを与えてはいけないので、コントローラ（操作系）の存在は空気のように意識されないものにする必要がある、とされます [S14]。
- 5原則は次のとおりです [S15]。

| # | 原則 | 意味 |
|---|---|---|
| 1 | 直感的で快適なインターフェイス | 操作で迷わせない・疲れさせない |
| 2 | マニュアル不要の操作理解 | 説明書を読まなくても遊べる |
| 3 | はまる演出 | 長時間集中して遊び続けたくなる |
| 4 | 段階的な学習効果 | いつの間にか上達している |
| 5 | リアルとバーチャルのリンク | 現実の体験と結びつける |

- ゲームニクスは、プレイヤーの先回りをして、**押しつけがましくないように、さりげなく支える**「おもてなしの文化」と説明されています [S14][S15]。

### 4-2. 必要になった瞬間に、必要なことだけ教える

- 『ブレス オブ ザ ワイルド』には開始時のチュートリアルがありません。武器を拾った瞬間に操作ガイドを出す、木に近づいたときに登れることを示すなど、その動作が必要になった瞬間にだけヘルプが出ます [S9]。
- これは、プレイヤーに「やらされている感」を与えず、自分から目標に向かった後に情報を表示するための工夫です [S9]。

### 4-3. テキストは最後の手段 ― 見ただけでわかる形にする

- 『スーパーマリオギャラクシー』の開発では、テストプレイヤーに意図が伝わらない場面がたくさんありました。その対処として、ステージを組み直したり、キャラクターにヒントを言わせたりしています。ただし、テキストでの解決は最後の手段であり、開発者にとっては敗北感があるものとして語られています [S16]。
- 代わりに、何をすればいいかが一目でわかるデザインで解決しようとしました。たとえば、トゲを見ればそれだけで痛そうだと伝わる、という例が挙げられています [S16]。

### 4-4. ステージ構成で遊び方を教える

- 初代『スーパーマリオブラザーズ』の最初のステージでは、キノコが土管に跳ね返ってプレイヤーの方へ向かってくる配置になっています。初めて遊ぶ人が敵か味方かわからずに避けようとしても、自然に取ることになり、キノコが良いものだと学べる仕組みです [S17]。
- 3Dマリオのステージは「導入 → 展開 → 転調 → 結末」という構成で作られています。ディレクターの林田宏一氏は、この考え方が「起承転結」から影響を受けたと述べています [S17]。
  - 導入：新しい仕掛けを安全な場所で見せる
  - 展開：同じ仕掛けで難度を少し上げる
  - 転調：別の要素と組み合わせて、違う見方を求める
  - 結末：腕試しで締める
- 『マリオ』シリーズは、失敗したときに作り手ではなく自分が悪いと思えるようなバランスで作られています。それが「もう1回」につながる、と語られています [S16]。

### 4-5. 触っているうちに機能が見つかる構造

- 『スーパーマリオメーカー』は、初めての人でも楽しめるわかりやすさと、コース作りのための高機能を両立させる必要がありました。わかりやすさと高機能は相反しやすいものです [S10]。
- 同作では、高機能を前面に出して教えることはしていません。アイテムを置くと何かしら反応が返ってくる作りにして、**触っているうちに機能を発見できる構造**にしています [S10]。
- 「機能が多くて覚えられない」という弱点を、「こんなこともできるんだ」という驚き、つまり発見する遊びに変えています [S10][S19]。
- 来場者のレポートでは、まずやさしい部分を体験して面白いと感じてもらい、触りながら覚えていく流れが紹介されています [S12]。

### 4-6. 「UI脳」と「娯楽脳」の二人三脚

- **UI脳**は、機能を満たすための定石です。たとえば「押せないボタンは薄くして押せないことを示す」「ピクトグラムは意味をはっきり伝える」といった知識です。仕事を効率化してくれる一方で、アイデアを制限することもあります [S10]。
- **娯楽脳**は、あそび心を考えて表現する思考です [S10]。
- 『マリオメーカー』では、受け付けられない組み合わせ（クリボーにキノコを与えるなど）を、事前にバツ印で塞ぐのではありませんでした。一度食べてから吐き出す、という反応にしています。UI脳だけでは出てこない発想の例です [S10]。
- まとめると、UI脳で娯楽脳を支え、娯楽脳でUI脳を加速させる、という関係です [S10]。
- 面倒な作業やつまらない作業も、発想を変えれば遊びに変えられます。「これは娯楽とは関係ない」とすぐに片付けないことが大切だとされています [S10][S11]。

### 4-7. 判定の幅：プレイヤーの意図を汲む

- CEDEC 2008のゲームニクスのラウンドテーブルでは、機械も人間も不完全である以上、多少ずれた入力でもプレイヤーの意図を汲み取って反映することが課題として議論されました。例として、少し方向がずれた攻撃でも一番近い敵に当たったと判定する、という話が出ています [S14]。
- ポインタ操作では、ポインタが近づいたボタンを自動で大きくするような工夫も考えられる、とされています [S14]。

### 4-8. 初めての体験と、予想の一つ先

- 初めての体験は貴重で、最初にどれだけ関心を持てるかがその後の関心を左右します。そのため、ファーストインプレッションを大切にしています [S10]。
- 「おもしろい」とは感情を動かすことであり、楽しさだけを指すわけではありません。ユーザーが予想する**一つ先の予想外**を用意しておくことが重要だとされています [S10]。

## 5. 快 ― 触って楽しい・魅力的

### 5-1. 音

- Switchの本体機能では、**移動・決定・遷移**の3つの操作音の心地よさにこだわっています。これらがテンポよく鳴ってつながることで、心地よさが生まれます [S1]。
- 具体的には次のような工夫が紹介されています [S2]。
  - カーソルを乗せたアイコンの種類によって、音の表情を変える
  - 連続して鳴る音のテンポを揃え、操作にリズムを生む
  - 遷移の前後で音をつなげる
- ホーム画面にBGMを流さないのも、「ゲームで遊ぶことに特化する」という考えからです。BGMによる演出を避け、その代わりに操作音の心地よさに力を入れています [S1]。
- 個人の観察では、ボタンを押した瞬間と移動が終わった瞬間の両方で音が鳴っていることが指摘されています。これは理解・操作・処理の流れに対応している、という考察です [S3]。
- 『スプラトゥーン』では、カーソルやボタンなど操作に反応して動く部分を、**音がなくても動かせば音が聞こえてきそうな形**にすることを目指しました [S12]。

### 5-2. 動き（UIアニメーション）

- シンプルなUIは、ともすると安っぽく見えます。『ブレス オブ ザ ワイルド』では、気づいてほしい情報を強調するためと、質感を保つためにアニメーションを使いました。重要なアイテムを手に入れたときにウィンドウが光る、といった表現です [S9]。
- アニメーションは、情報を伝える手段として使われています。ダメージを受けたときにハートが光って減ることで、その瞬間だけハートに目が向き、どれくらい減ったかを感覚的に把握できます [S9]。

### 5-3. 世界観と「らしさ」：わかりやすく、かつ新鮮に

- 『スプラトゥーン』のUIの狙いは「UIとしてわかりやすく、アートとして新鮮に」でした [S10]。
- 新鮮さはUIにとって危険でもあります。なじみのないUIは「わかりにくい」と拒否されることがあるからです [S10]。

**新鮮さの作り方** [S10][S11][S13]

- 自社の完成されたデザイン（『マリオ』など）を常に横に並べて比較し、新しさや品質の指標にしました。「らしくないもの」の基準として比較し続ける方法です [S11]。
- 形のデザインは、キーワード（「イカ」「スポーツ」）から連想される言葉を書き出し、それを形にするところから始めています。色がなくても『スプラトゥーン』だとわかるほど特徴的な形を目指しました [S10][S12]。
- 影色に黒を使わず、色相をずらした色（黄色の影にオレンジなど）を使って鮮やかな印象を作っています [S10][S12]。
- フォントは、太さでスポーツ感を、有機的な線で液体感を出しています。ただし最低限の可読性は守り、読みにくいと指摘された文字は最後まで修正を続けました [S10]。

**わかりやすさの保ち方**

- 明度・彩度の調整（2-8）、場面ごとの情報の優先度（2-5）で、個性の強いグラフィックでも画面がごちゃごちゃしないようにしています [S10][S13]。

### 5-4. 色・質感の統一

- 『ブレス オブ ザ ワイルド』では、文字やロゴの白を真っ白ではなく、少し黄色がかった白に統一しています。自然界に真っ白は存在しない、という考えによるものです。この色はやがて公式サイトやパッケージにも使われ、作品を象徴する色になりました [S9]。

### 5-5. トーン：「可愛らしさ」より「あたたかさ」

- 近年のカービィシリーズのUIは、作品ごとに違いはあっても、すべて「あたたかさ」で統一しています。キャラクターは可愛いと見られがちですが、シリーズには骨太なアクション作品が多いため、ゲーム性や世界観から離れないように気を付けている、という説明です [S6]。
- 幅広い年齢層が遊ぶため、難しそうに見せない、コントラストをきつくしすぎないなど、ユーザーを思いやる気持ちを「あたたかさ」と呼んでいます [S6]。
- 遊び心のあるデザインはやりすぎると、プレイヤーが見ているだけの過剰演出になります。そのさじ加減の難しさも語られています [S6]。
- 一方で、型にとらわれないグラフィカルなUIは、作品の魅力を直接伝える表現にもなります。例として、豊富なゲームモードを際立たせるリッチな選択メニューや、難易度の違いが一目でわかる選択画面が挙げられています [S6]。
- 時代やハードに合わせた挑戦もあります。タッチ操作が広まった時期の作品では、一目でボタンとわかる質感のある（スキューモーフィックな）デザインを採用しました [S6]。

### 5-6. 日常の「うれしい」から発想する

- 『ティアーズ オブ ザ キングダム』では、料理の写真を眺めて幸せな気持ちになる日常の感覚をヒントに、作った料理を眺められる「料理メモ」を作りました。これにより、さまざまな料理を作ること自体がご褒美になる、と説明されています [S8]。
- 地図を広げるワクワク感（3-6）と同じく、ゲームの外にある日常の感覚が発想の源になっています [S8]。

## 6. 遊んでいる人以外も含めて体験を設計する

### 6-1. 「将棋3席、麻雀5席」

- 将棋は2人、麻雀は4人で遊びますが、席を1つ多く用意する、というたとえです。ビデオゲーム以前から、娯楽には**遊んでいる人だけでなく、見ている人も楽しい**という価値がありました [S10]。
- 娯楽品に触れる人だけでなく、娯楽を取り巻く体験全体が娯楽である、という考え方です [S10][S19]。

### 6-2. 見ている人のための表示

- 『スーパーマリオメーカー』（Wii U）では、コースを作っている間、テレビ画面に大きな手が表示されます。邪魔に見えるかもしれませんが、作っている本人ではなく、隣で見ている家族や友だちが楽しめるようにした配慮です [S10][S11]。

### 6-3. 家族・保護者との関係まで設計する（Nintendo みまもり Switch）

- 当初は、制限・監視・強制終了の機能をスマートフォンに移すことを考えていました。しかし、それでは子どもの楽しみを損ない、親子関係にひびが入りかねないと気づきました [S10]。
- そこで、親子の会話のきっかけを作ることを軸に設計し直しています [S10]。
  - プレイ時間よりも先に、最近遊んだゲームのアイコンが目に入るようにする（会話のきっかけにする）
  - 日付ではなく曜日で表示する（親子の会話は曜日で行われるため）
  - 「よかった」「残念」といった機械的な評価やグラフは使わない（誤解やノイズを生むため）
  - いきなり強制スリープする中断モードの設定は、奥まった場所に置く（まず話し合うきっかけを作るため）
- アプリにとって一番大事な体験は、アプリの中ではなく外、つまり家族の笑顔にある、という結論です [S10]。

### 6-4. 家族全員が触れるもの

- Wiiの本体機能は「家族全員が触れる」をキーワードに検討されました。いろいろな趣味を持つ人がいる、という当たり前の認識から、ゲーム以外のチャンネルも用意しています [S5]。

## 7. 情報設計と全体の流れ

### 7-1. 仕様書を読み解き、ゲーム全体の流れで考える

- 仕様書どおりに作ったらゲームに合わなかった、画面上で情報が埋もれてしまった、という問題はよく起こります。カービィチームはその原因を、全体の流れが見えていないことにあると整理しています [S6]。
- 対策として、UIチームは仕様書を読んだうえでプランナーと打ち合わせをします。そして、実際に使われる場面や、同時に表示される他の情報を考えて整理します [S6]。
- 表示されるUIの外側にも目を向け、前後のつながりやゲーム全体の流れへの影響を考えることが大切だとされています [S6]。

### 7-2. UIは画面全体の一部

- 『スプラトゥーン』では、UIの見やすさをUIデザイナーだけでは調整できませんでした。背景の担当者に、ポスターを外したり背景をぼかしたりしてもらう必要がありました。チーム全体がUIの重要性を理解していたので、そうした依頼もしやすかったそうです [S10]。

## 8. 開発プロセス

### 8-1. 全員で触って共通認識を作る（ロムフェス）

- Switch本体機能のチームは「ロムフェス」という社内イベントを開いていました。部署を越えてチーム全員が試作品（ROM）を触り、良い点・悪い点を言い合います。課題を次の回までに解決する、というサイクルを繰り返しました [S1][S4]。
- 「あたりまえ」を手応えのある水準まで磨けた理由について、チームは、職種をまたいだ全員が同じ体験をして共通認識を持てたことだと分析しています。チームの方向が揃っていないと感じたら、コストをかけてでも全員で同じ体験をすべきだ、としています [S1]。
- 問題を解決する方法が分かっていても、立場上それを通せないことはよくあります。セクションを越えて問題を共有し、解決方法を探る仕組みが不可欠だ、という見方が紹介されています [S4]。

### 8-2. 部署横断チーム

- Wiiの本体機能は、部署を横断したチームで開発されました。アイデアがすぐに共有され、良いところを互いに取り入れながら最短距離で進めた、と振り返られています [S5]。
- 本体機能チームは毎週集まっていましたが、初期には何も決まらない回もありました。それでも、その時間は無駄ではなかったと語られています [S5]。

### 8-3. ユーザーに近い立場での品質評価

- 任天堂は「マリオクラブ」という、ユーザーに近い立場で作品を評価する仕組みを持っています。その経験から、操作性の重要性と、ユーザー中心の操作性のノウハウが確立されたとされます [S14][S15]。

### 8-4. 早く見せて、早く合わせる

- 『スプラトゥーン』のフォントは、ラフな段階で早めに書き出していました。方向性が合っているかを、アートディレクターや他のデザイナーと早めに共有するためです [S10]。

### 8-5. 試行錯誤を速くする仕組み

- 『ブレス オブ ザ ワイルド』では、PC上でゲーム画面にUIを重ねてプレビューできるツールを用意しました。これによりUIデザイナーだけで試行錯誤できるようにしています [S9]。
- 同作では、アイテムアイコンを3Dモデルから自動生成し、大量のマップ画像も地形データから自動生成するなど、作業の効率化も図っています [S9]。
- カービィチームは、デバッグ段階で文字数の上限を確認できるようにし、ローカライズの手間を減らしました。開発環境を整え、デザインそのものに時間を使いたい、という考えです [S6]。

### 8-6. 実際の人で確かめる

- Switch本体機能を磨き抜いた後でも、子どもが触っているうちに言語設定が別の言語に変わってしまう、という予想外の出来事が起きました [S1][S2]。
- 『マリオギャラクシー』でも、テストプレイヤーの反応から「こんなに伝わらないのか」という場面が多く見つかっています [S16]。

→ 補足：理論でどれだけ詰めても、最終的な判断は、作った人以外が初見で触ったときの反応で行う必要があります。

## 9. よく起きるトレードオフと、任天堂の解き方

| トレードオフ | 解き方の例 | 出典 |
|---|---|---|
| 多機能 ↔ 簡単そう | 混ぜない・サイズと密度・上下・少なく見せる | [S1] |
| わかりやすさ ↔ 高機能 | 触っているうちに発見できる構造、弱点を遊びに変える | [S10] |
| わかりやすさ ↔ 新鮮さ | UIとしてわかりやすく、アートとして新鮮に。既存デザインと比較する | [S10] |
| 誤操作防止 ↔ 軽快さ | 信頼と端的。誤操作は確認の多さではなく表示のわかりやすさで防ぐ | [S1] |
| 速さ ↔ 何が起きたか伝わること | 最小限のアニメーションを残し、約0.2秒に | [S1] |
| UIの存在感 ↔ 情報伝達 | 存在感は抑えつつ、必要な情報だけアニメーションで強調 | [S9][S8] |
| 常時表示 ↔ 没入 | 必要なときだけ表示、オプションで表示を減らす | [S9] |
| 遊び心 ↔ 過剰演出 | 世界観のトーン（「あたたかさ」など）でさじ加減する | [S6] |
| 保護者の要望 ↔ 子どもの楽しさ | 制限より会話のきっかけ、評価を押し付けない | [S10] |
| 階層化による整理 ↔ すぐ遊べること | 階層を深くしない | [S5] |

## 10. 参考：将棋ゲームへの適用例

以下は、出典の考え方を将棋ゲームに当てはめた**応用例**です。出典に直接書かれている内容ではありません。

| 原則 | 将棋ゲームでの適用例 |
|---|---|
| 主役を決める（2-1） | 盤面を最も大きく・濃く表示する。手番と持ち駒を次に重要な情報として扱い、メニュー類は小さくまとめる |
| 迷う配置をやめる（2-2） | 駒の選択・選択解除・移動・打つ操作の手順と見た目を、すべて同じルールに揃える |
| 視覚と聴覚の両方で伝える（2-3） | 王手、成り、指せない手を、表示と音の分類で一貫させる |
| 階層を浅く（2-4） | タイトル画面から対局開始までの画面数を最小にする |
| 場面ごとの優先度（2-5） | 対局中は盤面の情報を最優先にし、解説やヒントは必要なときだけ出す |
| 斜め読み・動詞ボタン（3-5） | 「成る／成らない」「投了する／対局を続ける」のように、ボタンを動詞にする |
| 信頼と端的（3-4） | 選択の余地がない処理（行き所のない駒が必ず成る場合など）は、そもそも質問しない。投了など取り返しのつかない操作の確認は残し、文言・ボタン・初期フォーカスをわかりやすくする |
| 処理は速く、でも伝わるように（3-3） | 相手（CPU）の指し手は、目で追える最小限の動きと強調表示で見せる |
| 待ち時間を価値に（3-6） | CPUの思考中に、局面に関係する豆知識や考え方のヒントを出す |
| 必要な瞬間に教える（4-2） | 初めて駒を取ったとき、初めて成れるとき、初めて王手したときに、1つずつ教える |
| テキストは最後の手段（4-3） | 移動できるマスの表示や、取れる駒の強調など、見ればわかる表現を優先する |
| 起承転結のステップ（4-4） | 学習レッスンを「導入（駒1種）→展開（難度を上げる）→転調（他の駒と組み合わせる）→結末（腕試し）」で構成する |
| 触って発見（4-5） | 定跡や囲いなどの高度な機能は、触るうちに見つかるように配置する |
| 反則への娯楽脳的な反応（4-6） | 二歩などの反則をただ禁止するのではなく、駒がぷいっと戻るなど、責めない反応で返す |
| 「将棋3席」（6-1） | 対局者以外（隣で見ている友だち、展示の見物人）にも局面や盛り上がりが伝わる表示にする |
| 全員で触る（8-1）・実際の人（8-6） | 将棋を知らない人に説明なしで触ってもらい、手が止まった場所を記録する |

## 11. チェックリスト

### 11-1. コンセプト・基本思想

- [ ] この画面（ゲーム）が何に特化するのか、一言で言えるか [1-4]
- [ ] 作らないと決めたもの・捨てたものを明確にしたか [1-4]
- [ ] わかりやすさだけでなく、魅力・楽しさも目標に入っているか [1-2]
- [ ] 文字を読まなくても主要な操作ができるか [1-3]
- [ ] 触ってみて「さわりたい」と感じられるか [1-6]

### 11-2. 明快

- [ ] 画面の主役が一目でわかるか（大きさ・密度・位置） [2-1]
- [ ] 種類の違うものを混ぜて並べていないか [2-1]
- [ ] 重要なものから順に上（目に入りやすい位置）に置いているか [2-1]
- [ ] 数が多い要素を、区切りやレイヤーで少なく見せているか [2-1]
- [ ] 実際に簡単なだけでなく、簡単そうに見えるか [2-1]
- [ ] 開発者自身が「どう動くべきか」で迷う配置がないか。迷うなら配置自体を見直したか [2-2]
- [ ] カーソル（選択）の移動先を、誰でも予測できるか [2-2]
- [ ] 見た目・挙動・音のルールが文書化され、全画面で統一されているか [2-2][2-3]
- [ ] メッセージの種類は少なく整理され、見た目と音が対応しているか [2-3]
- [ ] 伝えたいことを視覚と聴覚の両方で伝えているか [2-3]
- [ ] よく使うものが深い階層に埋もれていないか [2-4]
- [ ] 場面ごとに情報の優先度を見直し、主役（ゲーム画面）を隠していないか [2-5]
- [ ] 常時表示が本当に必要な情報だけになっているか。必要なときだけ表示できるものはないか [2-5]
- [ ] 存在感は抑えつつ、必要な情報は確実に目に入るか [2-6]
- [ ] 画面の構図だけで関係性（AとBでCになる、など）が伝わるか [2-7]
- [ ] 白黒にしたり目を細めたりして見たとき、重要な情報が浮かび上がるか [2-8]
- [ ] 目立たせたい要素だけ彩度が高くなっているか [2-8]
- [ ] 情報過多（選択肢が多すぎる）や情報不足（番号だけ、など）になっていないか [2-9]

### 11-3. 軽快

- [ ] 電源（ページ）を開いてから遊び始めるまでの時間と手数は最小か [3-1]
- [ ] 主な操作について、理解・操作・処理の3つの時間をそれぞれ見直したか [3-2]
- [ ] 処理が速すぎて何が起きたかわからない、ということはないか [3-3]
- [ ] 初期カーソルや既定の選択が、ユーザーの意図に沿っているか [3-4]
- [ ] 選択の余地がない処理について、わざわざ質問していないか（取り返しのつかない操作の確認は残す） [3-4]
- [ ] 誤操作の防止を、確認の多さではなく表示のわかりやすさで実現しているか [3-4]
- [ ] 文の冒頭に主題があり、決定ボタンが動詞になっているか（「はい／いいえ」になっていないか） [3-5]
- [ ] 冒頭と最後を読むだけで内容が伝わるか [3-5]
- [ ] アイコンが文章の理解を邪魔していないか [3-5]
- [ ] 待ち時間を、役に立つ時間やワクワクする時間に変えられないか [3-6]

### 11-4. おもてなし・学習設計

- [ ] 遊ぶ前に長い説明を読ませていないか [4-1][4-2]
- [ ] 新しいことは、必要になった瞬間に1つずつ教えているか [4-2]
- [ ] 「やらされている感」を与えていないか。プレイヤーが自分から動いた後に情報を出しているか [4-2]
- [ ] テキストで説明する前に、形・配置・動きで伝えられないか検討したか [4-3]
- [ ] 学習の流れが「導入 → 展開 → 転調 → 結末」のように段階的になっているか [4-4]
- [ ] 失敗したとき、作り手ではなく自分のせいだと納得でき、もう1回やりたくなるか [4-4]
- [ ] 高機能を一度に教えず、触るうちに発見できる構造になっているか [4-5]
- [ ] 面倒な作業・弱点を遊びに変えられないか検討したか（UI脳＋娯楽脳） [4-6]
- [ ] 受け付けられない操作に対して、単に塞ぐ以外の楽しい反応を検討したか [4-6]
- [ ] 多少ずれた入力でも、プレイヤーの意図を汲んで判定しているか [4-7]
- [ ] 最初の数十秒の体験（ファーストインプレッション）を特に作り込んでいるか [4-8]
- [ ] ユーザーの予想の一つ先にある驚きを用意しているか [4-8]

### 11-5. 快・魅力

- [ ] 移動・決定・遷移の操作音が心地よく、テンポがそろっているか [5-1]
- [ ] 押した瞬間と、処理が完了した瞬間のフィードバックがあるか [5-1]
- [ ] 演出（BGMなど）が主役の体験を邪魔していないか [5-1]
- [ ] アニメーションは、気づいてほしい情報を伝える目的で使われているか [5-2]
- [ ] シンプルなデザインが安っぽく見えていないか [5-2]
- [ ] 世界観をキーワードで言語化し、形・色・フォントに落とし込んでいるか [5-3]
- [ ] 既存の完成されたデザインと並べて比較し、「らしさ」と品質を確認したか [5-3]
- [ ] 新鮮さを追求しても、可読性は守られているか [5-3]
- [ ] 色や質感が作品全体で統一されているか [5-4]
- [ ] 作品のトーン（例：「あたたかさ」）が決まっていて、UIがそれに沿っているか [5-5]
- [ ] 幅広い人が遊ぶ場合、難しそうに見せない・コントラストをきつくしすぎない配慮があるか [5-5]
- [ ] 遊び心が過剰演出になっていないか [5-5]
- [ ] 日常の「うれしい」「ワクワク」から発想した要素があるか [5-6]

### 11-6. 体験全体

- [ ] 遊んでいる人以外（見ている人、家族、友だち）も楽しめるか（「将棋3席」） [6-1][6-2]
- [ ] 周囲の人との関係を悪くするような設計（機械的な評価、一方的な制限）になっていないか [6-3]
- [ ] いろいろな趣味・経験の人が触ることを想定しているか [6-4]

### 11-7. 情報設計・チーム

- [ ] 個々の画面だけでなく、前後の画面やゲーム全体の流れの中でUIを考えたか [7-1]
- [ ] 同時に表示される他の情報（背景・キャラクター・エフェクト）とのバランスを確認したか [7-2]
- [ ] 職種や担当の違う人と同じ試作品を触り、意見を出し合ったか [8-1][8-2]
- [ ] ラフな段階で早めに方向性を共有したか [8-4]
- [ ] 試行錯誤を速く回せる環境（プレビュー、自動生成、文字数チェックなど）があるか [8-5]
- [ ] 作った本人以外（ゲームに慣れていない人、子ども）に、説明なしで触ってもらったか [8-6]
- [ ] テストで見つかった「伝わらない」場所を、テキストを足す以外の方法で解決したか [4-3][8-6]
