# UI_Nintendo_Design ― 将棋WebアプリのUI設計仕様

画面・機能を**設計するとき**に使う仕様書です。何を作るか、画面に何をどの順で見せるか、どの操作でどう応えるかを決める段階で参照します。
実装時のルール（数値・コンポーネント・コード上の決まり）は `UI_Nintendo_Implementation.md` にまとめています。
各ルールの根拠は `UI_Nintendo.md` の章番号で示しています（例：`→N:3-5`）。

---

## 1. 前提

書き換え可能な前提です。前提が変わったら、2章の優先順位と9章のチェックを見直します。

| 項目 | 内容 |
|---|---|
| アプリ | ブラウザで動く将棋ゲーム（PC・スマートフォン・タブレット） |
| 主な利用者 | 将棋の初心者（駒の動かし方を知らない人を含む）、子どもから大人まで |
| 利用場面 | 文化祭での展示。予備知識のない来場者が数分間触る。説明係がいないこともある |
| 目的 | 遊びながら将棋の基本を覚えられること |
| コンセプト | **「説明を読まずに、触っているうちに将棋が指せるようになる」** |
| 作らないもの | 対局と学習に関係しない機能（詳細な統計、アカウント管理、多数の設定項目など）。追加するときは、このコンセプトに合うかで判断する（→N:1-4） |

---

## 2. 判断の優先順位

原則同士がぶつかったときは、上を優先します（→N:1-6, 9）。

1. **迷わない・間違えない**（明快）
2. **待たせない・手数が少ない**（軽快）
3. **説明なしで伝わる**（おもてなし）
4. **触って気持ちいい**（快）
5. **見た目の新鮮さ・装飾**

上位の項目が満たされていない箇所には、下位の項目の改善（演出の追加など）を入れません。

## 3. 画面構成と導線

### 3-1. 画面一覧（最小構成）

| 画面 | 主役 | 目的 |
|---|---|---|
| タイトル | 「はじめる」ボタン | すぐに遊び始める |
| モード選択 | 2〜3個の選択肢 | 「レッスン」か「対局」か選ぶ。選択肢は3つ程度まで（→N:2-1） |
| 対局 | 盤面 | 指す |
| レッスン | 盤面＋短い目標表示 | 1つのことを覚える |
| 結果 | 勝敗と「できるようになったこと」 | 達成感と次の目標 |
| 設定 | ― | 音量・補助表示のオン／オフなど最小限。メニューの奥に置く |

### 3-2. 導線のルール

- タイトルから盤面が出るまでの操作は**最大2回**（例：「はじめる」→「レッスン」）（→N:3-1, 2-4）。
- 階層は浅くします。よく使う画面を設定やサブメニューの奥に置きません（→N:2-4）。
- どの画面からも、1回の操作でタイトルに戻れます。
- 一定時間操作がなければタイトルに戻ります。対局中は戻る前に予告します（展示用）。

## 4. 情報の優先順位（画面ごと）

各画面で「何を一番目立たせるか」を決めておきます。重要度は**大きさ・濃さ（彩度・コントラスト）・位置**で表します（→N:2-1, 2-8）。

### 4-1. 対局画面

| 優先度 | 要素 | 表現 |
|---|---|---|
| 1 | 盤面と駒 | 最大サイズ。画面中央 |
| 2 | 手番 | 手番側の持ち駒エリア・名前欄を強調する。文字だけで示さない |
| 2 | 直前の一手 | 移動元・移動先を薄く色付けして常に表示する |
| 3 | 自分の持ち駒 | 盤の手前側（画面下） |
| 3 | 相手の持ち駒 | 盤の奥側（画面上） |
| 4 | 状態表示（王手・考え中など） | 必要なときだけ出す（→N:2-5） |
| 5 | 操作ボタン（待った・投了・メニュー） | 小さくまとめ、盤面と競合させない |

- 対局中は、対局に不要な情報（長い説明文、詳細な設定など）を常に表示しません（→N:2-5）。
- 補助表示（動けるマス、ヒント）を消せる設定を用意し、慣れた人向けにします（→N:2-5「プロモード」）。

### 4-2. レッスン画面

- 対局画面と同じ盤面・同じ操作ルールを使います。画面ごとに操作を変えません（→N:2-2）。
- 目標を短く1行で常に表示します（例：「玉を詰ませよう」）。
- 説明文は「必要になった瞬間に1つだけ」出します（6章）。

### 4-3. 結果画面

- 勝敗よりも先に、「できるようになったこと」と「次の目標」を見せます（→N:4-8, 5-6）。
- 「残念」「失敗」など、プレイヤーを評価する表現は使いません（→N:6-3）。

## 5. 操作とフィードバックの設計

### 5-1. 駒の操作ルール（全画面共通）

開発者が「この場合どうなるべきか」で迷う操作は、ユーザーも迷います。迷う場合は、操作の仕組みそのものを単純にします（→N:2-2）。

| 操作 | 結果 |
|---|---|
| 自分の駒をタップ | その駒を選択する。動けるマスを表示する |
| 選択中に動けるマスをタップ | 移動する |
| 選択中に同じ駒をタップ | 選択を解除する |
| 選択中に別の自分の駒をタップ | 選択がその駒に移る |
| 選択中に動けないマスをタップ | 選択を解除する（エラー扱いにしない） |
| 持ち駒をタップ | 盤上の駒と同じ流れ（選択 → 打てるマスを表示 → タップで打つ） |
| ドラッグ | タップと同じ結果になる（どちらでも操作できる） |

### 5-2. 確認ダイアログの方針

「信頼と端的」の考え方を使いますが、**確認をなくすことが目的ではありません**。変えるのは、質問の要否、文言、初期フォーカスです（→N:3-4）。

| 操作 | 取り消せるか | ダイアログ | 初期フォーカス |
|---|---|---|---|
| 成りが強制される移動（行き所のない駒） | ― | 出さない（自動で成る） | ― |
| 成る／成らないを選べる移動 | 移動確定前なら可 | 盤上で選択肢を出す | 成るのが自然な場面では「成る」 |
| 待った | 可 | 出さない | ― |
| 投了 | 不可 | 出す | 「対局を続ける」 |
| 対局をやめてタイトルへ | 不可（対局が消える） | 出す | 「対局を続ける」 |
| 学習の進み具合をリセット | 不可 | 出す | 「キャンセル」 |
| 音量・表示設定の変更 | 可 | 出さない | ― |

- ダイアログの文は**主題を先頭**に置き、ボタンは**動詞**にします。「はい／いいえ」は使いません（→N:3-5）。
- 確認を出しすぎると、本当に重要な確認が読まれなくなります。確認は上の表に挙げたものに限ります。

### 5-3. メッセージ分類

メッセージは4つの分類に限定し、分類ごとに見た目と音を1対1で対応させます（→N:2-3）。新しいメッセージを追加するときは、まずどの分類に入るかを決めます。

| 分類 | 用途の例 | 見た目の方向性 | 音の方向性 |
|---|---|---|---|
| 通常 | 手番の交代、案内 | 落ち着いた標準表示 | 短く軽い音 |
| 注目 | 王手、成れる、詰みが近い | 目立つが怖くない | 注意を引く音 |
| 不可 | 指せない手を試した | 控えめで柔らかい。責めない | 小さく柔らかい音 |
| 特別 | 勝利、レッスン達成、初めての成功 | 特別感のある表示 | 嬉しい音 |

- 「特別」は乱発しません。
- 情報は**視覚と聴覚の両方**で伝え、どちらか一方だけで意味が伝わるようにします（会場の騒音や、音を消している環境を想定）。

### 5-4. 反則の扱い

- 反則になる手（二歩、行き所のない駒、打ち歩詰め、王手放置など）は、**動けるマスに表示しない**ことで、最初から選べないようにします（→N:4-6 の UI脳）。
- それでも試みた場合（ドラッグでの誤操作など）は、「不可」分類で柔らかく理由を伝えます。例：駒が元の位置にぽんと戻り、「同じ列に歩は2枚置けないよ（二歩）」と表示する（→N:4-6 の娯楽脳）。
- 初心者向けのモードでは反則負けにしません。

## 6. 学習設計（説明しないで教える）

### 6-1. 基本方針

- 最初に長いチュートリアルを読ませません（→N:4-2）。
- 新しいことは**必要になった瞬間に1つだけ**教えます（→N:4-2）。
- 文章で説明する前に、盤面の状況と見た目で気づかせます。テキストは最後の手段です（→N:4-3）。
- 失敗したときに「自分の指し方が原因だった」と納得でき、もう1回やりたくなる難しさにします（→N:4-4）。

### 6-2. 初回ヒントの一覧（各1回だけ表示）

| きっかけ | 教えること | 伝え方 |
|---|---|---|
| 初めて駒を選んだ | 光っているマスに動かせる | 一言だけ。2回目以降は出さない |
| しばらく操作がない | どの駒を動かせるか | 動かせる駒をそっと光らせる |
| 初めて駒を取った | 取った駒は自分の持ち駒になる | 取った駒が持ち駒エリアへ飛んでいく動き |
| 持ち駒ができた直後の手番 | 持ち駒は盤に打てる | 持ち駒を軽く光らせる |
| 初めて成れる | 成るとは何か | 成った後の駒を見せて選ばせる |
| 初めて王手した／された | 王手の意味 | 盤上の強調と一言 |

### 6-3. レッスンの構成

各レッスンは「導入 → 展開 → 転調 → 結末」で構成します（→N:4-4）。

| 段階 | 内容 | 例（飛車のレッスン） |
|---|---|---|
| 導入 | 新しい要素を、失敗しにくい状況で1つ見せる | 飛車だけを置いた盤で、まっすぐ動くことを体験する |
| 展開 | 同じ要素で少しだけ難しくする | 遠くの駒を取りに行く |
| 転調 | 他の要素と組み合わせる | 他の駒が邪魔をしている状況で使う |
| 結末 | 腕試しで締める | 飛車を使って玉を詰ませる |

- レッスンの順番は「簡単なこと → 難しいこと」にし、一度に覚えることを1つにします（→N:4-1 段階的な学習効果）。
- 高度な内容（定跡や囲いなど）は前面に出さず、触っているうちに見つかる場所に置きます（→N:4-5）。

## 7. 快の設計（不快を除いた後に足す）

### 7-1. 音

| 種類 | 設計の方向性 |
|---|---|
| 駒を置く音 | 気持ちよさの中心。短く、はっきりしていて、何度聞いても疲れない |
| 駒を取る・成る・打つ | 駒を置く音を少し変化させる |
| メニューの移動・決定・戻る | テンポを揃え、連続して押したときにリズムが生まれるようにする（→N:5-1） |
| 画面遷移 | 遷移前後の音をつなげる（→N:5-1） |
| BGM | 対局中は、駒音を邪魔しない程度か、なしにする（→N:5-1 ホーム画面にBGMなし） |

### 7-2. 動き

- アニメーションは**情報を伝えるため**に使います。気づいてほしいもの（王手、取った駒の行き先、相手の指し手）だけを動きで強調します（→N:5-2）。
- 演出は短く、スキップできるようにします。演出のせいで操作を待たせてはいけません（→N:3-3, 5-5）。

### 7-3. 見た目のトーン

次の項目は、制作中に決めて記入します（→N:5-3〜5-5）。

| 項目 | 決定内容 |
|---|---|
| トーンを表すキーワード | （例：「あたたかい」「木と紙」） |
| キーワードから連想した言葉 | （例：将棋盤の木目、和紙、墨、扇子） |
| 色の方針 | （例：影に黒を使わず、色相をずらす。コントラストをきつくしすぎない） |
| フォントの方針 | （例：駒の文字は読みやすさを最優先。UI文字は丸みのあるゴシック体） |
| 比較対象 | 既存の将棋アプリを並べて比較し、「らしさ」と見やすさを確認する |

- 新鮮さよりも可読性を優先します（→N:5-3）。
- 幅広い年齢の人が遊ぶので、難しそうに見せないようにします（→N:5-5）。

### 7-4. 日常の「うれしい」

- 結果画面や学習の記録に、「集めて眺めるとうれしい」要素を検討します。例：覚えた駒の動きが図鑑のように埋まっていく（→N:5-6）。

## 8. 対局者以外への配慮（将棋3席）

- 隣で見ている人や、展示を通りかかった人にも、局面や盛り上がりが伝わる表示にします（→N:6-1, 6-2）。
  - 例：王手や駒を取った瞬間の演出は、少し離れた場所からでも見える大きさにする
  - 例：直前の一手を常に表示し、途中から見た人にも状況がわかるようにする
- 盤面と駒の文字は、少し離れた場所から複数人がのぞき込んでも読める大きさにします。
- 評価や点数で対局者を「良い・悪い」と判定しません（→N:6-3）。

## 9. 設計レビューのチェックリスト

画面・機能の設計を確定する前に確認します。

**コンセプト**
- [ ] この機能はコンセプト（1章）に合っているか。合わないなら作らない判断をしたか
- [ ] 優先順位（2章）の上位を犠牲にして、下位の項目を満たしていないか

**導線・情報**
- [ ] タイトルから盤面まで、操作2回以内か
- [ ] 画面ごとの主役（4章）が、大きさ・濃さ・位置で表現されているか
- [ ] 同じ種類の選択肢が3つ程度に収まっているか。収まらない場合はグループ分けしたか
- [ ] 常時表示が本当に必要な情報だけになっているか

**操作**
- [ ] 駒の操作ルール（5-1）から外れた操作を作っていないか
- [ ] 確認ダイアログは5-2の表に沿っているか。選択の余地がないことを質問していないか
- [ ] 新しいメッセージは5-3の4分類のどれかに入っているか
- [ ] 反則手を、そもそも選べないようにしているか

**学習**
- [ ] 文章を読まなくても始められるか
- [ ] 新しいことを、必要な瞬間に1つずつ教えているか
- [ ] テキスト以外（配置・見た目・動き）で伝える方法を先に検討したか
- [ ] レッスンが「導入→展開→転調→結末」になっているか

**快・体験全体**
- [ ] 不快（迷い・待ち・誤操作）の除去が終わった箇所にだけ演出を足しているか
- [ ] 演出は短く、スキップできるか
- [ ] 見ている人にも状況が伝わるか
- [ ] プレイヤーを責める・評価する表現がないか

**検証の計画**
- [ ] 将棋を知らない人に説明なしで触ってもらうテストを予定しているか（→N:8-6）
- [ ] テストで見る点を決めたか（最初の操作までの時間、手が止まった場所、誤操作、説明を読んだか、表情）

## 10. 機能設計メモのテンプレート

新しい画面や機能を設計するときは、次の項目を埋めます。

```markdown
### 機能名：

- 目的（コンセプトとの関係）：
- 利用場面（誰が・いつ・どのくらいの時間）：
- 画面の主役：
- 情報の優先順位（1〜5）：
- 操作の流れ（手数）：
- 確認ダイアログ（有無・理由・初期フォーカス）：
- 使うメッセージ分類：
- 初めて使う人への伝え方（テキスト以外の方法）：
- 快の要素（音・動き）：
- 見ている人への配慮：
- 作らないと決めたこと：
- 検証方法：
- 根拠（UI_Nintendo.md の章番号）：
```
